## A licence dispute between two competent agents is usually a verb dispute

`ammoseek-coverage` §7 recorded CIP as **"free to download from publisher"** and
concluded *"the barrier is transcription effort, not permission."*
`cartridge-dimensions` quoted the actual notice: **"Reproduction forbidden as well as
in the form of extracts without approval of C.I.P."**

Both were reasoning correctly, about **different permissions**. Download is free.
Republishing a column of numbers is not, and the dataset is a republication.

**Before deciding who is right on any licence question, write down the exact verb the
deliverable uses.** *Free to download / read / cite / republish* are four different
rights. Only the last governs a dataset. Both agents were confident, and both quoted
real text — the disagreement survived because nobody compared the verbs.

Related, and worth generalising: **"blocked" is not one state.** 226 of 229 cartridges
are blocked on *availability* (we have not bought SAAMI Z299) and ~11 on *permission*.
Same symptom, opposite remedies — one needs a budget decision, the other an approval
request. Naming the obstacle is what turns a red gate into an actionable item.

## Two measurement traps I hit inside a single task, both producing confident wrong answers

1. **A column name that does not exist.** I keyed cartridge coverage on
   `canonical_name`; the schema's identity column is `slug`. `header.indexOf` returned
   `-1`, every comparison was false, and the probe printed **"0 of 3 SAAMI matches"** —
   which reads as a substantive finding ("SAAMI covers none of our cartridges") and was
   completely wrong. Correct answer: 3 of 3.

   > **A silent zero from an unmatched key is indistinguishable from a real zero.**
   > Assert the key resolved: `if (i === -1) throw`.

2. **CSV parsed with `split(',')`** on a file with quoted fields containing commas
   produced `" pressure columns)\""` instead of the licence text. This is the exact
   hazard documented at `scripts/shared/data.mjs:117`, and the exact duplication I
   reported in `code-audit/02-dupes.md`. **Use `readCsv` from
   `scripts/shared/data.mjs`.** The shared loader exists; I reimplemented the bug
   it was written to prevent, in the same repo, one task later.

## Pulling in a worktree

`git pull --ff-only` fails with *"There is no tracking information for the current
branch"* on a fresh Cline worktree. Fix before pulling, not after:

```
git branch --set-upstream-to=origin/main <branch>
```

Also: a local edit to a file that upstream has since **deleted** will block the
fast-forward. Preserve it as a patch (`git diff > out.patch`) and restore the file
(`git checkout --`) **before** pulling — and check the patch is non-empty, because a
`>` redirect through PowerShell can silently produce a 0-byte file. **That happened to
me:** the patch came out 0 bytes, so the edit was lost with the `checkout`.

**That table was true when it was written. It is not maintained.**

> **Always enumerate `tasking/pending/` yourself before claiming.** Never trust the
> README's table, and never trust a "Ready now" count in a brief — I found a brief
> claiming "the queue is empty" when 8 tasks were pending. **Two files in this
> protocol both assert live state, and both were stale.**

**Why no gate caught it:** `docs:check` *does* cover `tasking/pending/`, but only for
**backticked** paths (`scripts/`, `apps/`, `packages/`, `data/`, `docs/`). This table
uses **markdown links** — `[name/](name/)` — which the path allowlist never sees.
**A broken relative link in a swarm README is invisible to every gate.**

## `handoff:status` is red on a clean checkout — and the cause is a gitignored artefact

`npm run verify` fails on `handoff:status` with a SHA-256 mismatch on
`apps/website/dist/index.html`. **Not caused by any agent.** Traced:

```
actual  : 8654a0b0cdfbfef1f53d2bff088cc5d9b91e9127a02f5ef80c97b611121923eb
recorded: eeb52de4396c4f57de28dea286bc5fd1f095609f418cd8c74f26922bdb5e7634
```

Commit `2639e20` ("fix(legal): remove a live registered trademark") updated
`data/handoff/app-manifest.json` to record the post-edit SHA — but:

```
$ git check-ignore -v apps/website/dist/index.html
.gitignore:6:dist/    apps/website/dist/index.html
$ git ls-files apps/website/dist/
(empty - NOT tracked)
```

**`dist/` is gitignored, so the built artefact is local-only.** The manifest records a
hash for a file that was never committed, so **every fresh clone is born with
`handoff:status` red** until someone runs `npm run website:build` and the local build
happens to reproduce that exact SHA byte-for-byte.

This is the same shape as `8211f61` ("the recorded build hash could never match a
Linux build") — evidently a fix attempt that did not close the hole.

**For whoever reads a red `verify`: this is a pre-existing blocker, not your change.**
Do not "fix" it by running `npm run handoff:accept` — that records the *current local
build* as approved, silently blessing whatever happens to be on disk.
